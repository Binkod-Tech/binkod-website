AI Engineering Lab

How intelligent applications work

Explore the building blocks behind AI-powered applications — from language models and knowledge retrieval to tool-enabled workflows and evaluation. Educational notes from our learning journey.

This section explains general patterns we're studying. Nothing here claims that a particular model or system powers a live BINKOD product.

01

Understanding language models

What a model actually does with a prompt — and why context matters.

A language model predicts text token by token. Given a prompt — your instructions plus any context the system supplies — it generates a response one piece at a time, informed by patterns learned during training. OpenAI's GPT-family models are one example of the hosted model services in this space.

The output is only as good as the instructions and the context it receives. A vague prompt with thin context produces a vague result, and because models generate text rather than look up facts, they can also produce answers that sound right but are not supported — so developers evaluate outputs against test questions instead of trusting them.

  • A prompt includes the instructions, the question and any context the system chooses to supply.
  • Generation is probabilistic — the same prompt can produce different wording each time.
  • Clear instructions and relevant context improve reliability more than clever wording.
  • Models can be confidently wrong; grounding and evaluation are how applications compensate.
  • Developers test representative questions and check whether answers are supported by the source material.
02

Retrieval-Augmented Generation (RAG)

Giving a model the right context to answer with — and showing where answers come from.

  1. Approved sources Documents from places you control.
  2. Prepare & chunk Split into meaningful passages.
  3. Embed & index Passages become searchable vectors.
  4. Retrieve & rank The closest, allowed passages are chosen.
  5. Ground & answer The model answers from that context.

A question travels down this path — retrieval decides what the model gets to see.

Data preparation & parsing

Documents are collected from approved sources, extracted to text and normalised. Access rules are applied from ingestion onward, so restricted content never becomes answerable by accident.

Chunking strategies & metadata

Content is split into meaningful chunks — by structure, by semantic boundaries, or with deliberate overlap — and each chunk keeps metadata such as source, section and permissions that later supports filtering and traceability.

Embedding generation

Each chunk is converted into a vector embedding that captures its meaning rather than its exact words, then stored in a search index or vector database.

Retrieval, ranking & reranking

The query is embedded and the index returns candidates by similarity. Keyword search, metadata filters and access rules can narrow those candidates, and a reranking step can reorder them by relevance.

Context construction & generation

The best passages are assembled into a grounded prompt alongside the question. The model answers from that context, and citations can point back to the sources where supported.

Access control & quality evaluation

Retrieval only exposes content the requester is allowed to see, and answers are evaluated for grounding and relevance. When answers miss, retrieval quality is usually the first thing to improve.

03

Embeddings & vector search

Finding content by meaning, not just by matching words.

  • Query embedding
  • Closest matches
  • Further away / filtered out
  • A user submits a question.
  • The question is turned into an embedding — a numeric representation of meaning.
  • Search retrieves the closest content by similarity, not just shared keywords.
  • Metadata filters and access rules constrain which results are eligible.
  • Candidates are ranked — and reranked where the extra step adds value.
  • The retrieved passages ground the model's answer.

A conceptual illustration of a vector space — not a projection of a real embedding store. With a metadata filter applied, content outside the eligible set stops being retrievable.

04

AI agents & MCP

When a model uses approved tools to get things done.

01 Receive a request
02 Interpret intent
03 Retrieve knowledge
04 Select an approved tool
05 Run an authorised action
06 Check the result
07 Return a grounded response

A basic model call answers from its prompt and context. A RAG workflow adds retrieval so answers are grounded in your own content. An agentic workflow goes further: it can interpret a request, decide what it needs, choose from a fixed set of approved tools and check its own result before responding.

MCP (Model Context Protocol) is an open way for AI applications to connect to compatible tools and context sources through a consistent interface. Every tool an agent may call is authorised for that workflow — nothing is reachable by default.

Not every AI feature needs an agent. Many useful features are a single grounded model call — the simplest approach that works is usually the right one.

Model call One prompt, one response.
RAG Adds retrieved context for grounding.
Agent Adds approved tools and multi-step actions.
05

Evaluation, security & reliability

The engineering that makes an AI feature dependable.

An AI feature is only useful if it is dependable. That means measuring the quality of answers, protecting private data and watching how the system behaves in real use — the same discipline as any other part of software.

  • Test representative questions, not just easy ones.
  • Evaluate retrieval relevance and whether answers are grounded in sources.
  • Use human review where the stakes are higher.
  • Watch latency, errors and cost like any other system metric.
  • Protect private data and apply access controls at retrieval time.
  • Treat prompt injection and untrusted input as real risks.
  • Keep a human in the loop before sensitive actions.
  • Log enough to debug failures without storing what you should not keep.

AI architecture

Architecture behind intelligent software

Most applications — mobile, web, SaaS, CRM or internal tools — share the same basic layers. This is the general picture, with the AI parts clearly marked as optional.

  1. User interface
  2. API & backend
  3. Data & integrations
  4. AI orchestration optional
  5. Model & retrieval optional
  6. Validated response

An example request: someone asks a question in the interface, the backend validates it and gathers permitted data, the AI layers (when present) retrieve context and call the model, and a checked response travels back — with security and operations wrapping every layer.

Layer 1 — User interface

People interact through a mobile app, a website, a desktop client or another interface. It collects the request, shows progress and presents the answer — including sources or uncertainty where they matter.

Layer 2 — API & application backend

The backend receives requests, applies business rules and validation, checks identity and permissions, and coordinates every other component. It is the control point of the application.

Layer 3 — Data & integration

Databases, document stores, queues and external APIs hold the information and connect the system to other services. Data access is governed here by permissions and schema rules.

Layer 4 — AI orchestration optional

Only for AI-enabled features: this layer prepares prompts, retrieves relevant context, selects approved tools and coordinates model calls. Applications without AI simply do not have this layer.

Layer 5 — Model & retrieval systems optional

Language models, embeddings, search indexes and vector databases perform the AI and retrieval work the orchestration layer asks for. A vector database is only useful when a feature genuinely needs semantic search.

Layer 6 — Security & operations

Identity, authorisation, secrets, logging, monitoring, testing and deployment practices support every layer at once. Security is not a component added at the end — it wraps the whole system.

A reference view of how software is usually layered. Not every mobile, web, CRM or SaaS application needs a vector database or an AI agent — and this is general education, not a description of a deployed system.

Product engineering

Building software people can use

The practical principles behind how we design, develop, test and release software — a general approach that stays the same whether the product is mobile, web or a service.

  1. 01

    Understand

    Start from the real problem and who it is actually for.

  2. 02

    Design

    Shape the experience and the system before writing code.

  3. 03

    Build

    Small, reviewable steps built from reusable pieces.

  4. 04

    Test

    Check the edge cases and the errors, not just the happy path.

  5. 05

    Release

    Ship when it is genuinely ready — updates and fixes included.

  6. 06

    Improve

    Learn from real use, fix what matters, refine and repeat.

Understand the problem

Talk to the people who will use it, and build the smallest thing that genuinely helps.

Mobile-first & responsive

Start from the device people actually carry, then adapt cleanly to larger screens.

Simple, accessible interfaces

Plain language, strong contrast, and keyboard- and screen-reader-friendly interactions.

Reusable, maintainable code

Readable components and sensible structure so the next change stays easy.

Reliable APIs & data

Clear interfaces, careful validation and predictable error handling on every path.

Secure by default

Authentication, authorisation and least-privilege access as defaults, not add-ons.

Testing & release validation

Automated checks where practical, honest testing before release, and learning from what breaks.

Privacy, performance & battery

Collect only what a feature needs, and keep background work light and battery-aware.
